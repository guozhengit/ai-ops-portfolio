# 原型 3 设计：基础设施体检 Agent（W4，2026-10-30）

> 定位：把人做巡检的方法论固化成一条可复跑的流程。不是「又一个扫描器」，是
> **「把老运维脑子里那套『该看什么、什么算严重、看到之后怎么处置』写成代码，
> 并且能被外部裁判逐条打分」**。

## 一、先纠三个 planning 阶段的错

骨架 README 写在 W1，当时的假设今天探查全部推翻，先把错的钉在这里，免得以后照着抄：

1. **`hotel-booking/ops/port-audit/port_audit.py` 不存在**。全盘搜过 `D:\AI`，没有这个文件。
   骨架说「复用它的思路」是空头支票。真正可复用的是另外三份：
   - `agentscope-learning/tools/secret_scan.py`：分层判定（配置从严/代码从宽）、
     脱敏（只报键名+长度，绝不打印原文）、占位符不算违规、注释降级为 P2。
   - `hotel-booking/ops/check/schema_guard.py` 与 `ops/scripts/check_perm_parity.py`：
     **纯标准库、离线只读、退出码即门禁、白名单豁免必须落文件且注明归属、
     代码里绝不出现仓库外绝对路径字面量**。
   这三条纪律是原型 3 真正要继承的东西，比一个不存在的脚本值钱。
2. **靶场 IP 变了**。骨架写「159/160 真实环境」。实测 159 彻底不通（ping/22/9091 全 closed），
   本机 DHCP 后是 `192.168.1.16`。**160 活着**：SSH(22) 开着但免密三把私钥全被拒，
   Prometheus(9091) 只读 HTTP 通。所以采集层只走只读 HTTP，不赌 SSH。
3. **`.gitignore` 会吞检查器文件**。`**/*credential*`、`**/api_key*`、`**/*credential*`
   是全局规则。原型 2 的 `ApiKeyAuthFilter.java` 已经被这套规则静默吞过一次（本地绿、CI 红）。
   所以检查器命名为 `credscan.py` 而非 `credential_scan.py`，写完必须 `git check-ignore` 复查。

## 二、改写后的任务（抬一层）

表层任务：写三个检查脚本，扫端口、扫密钥、查配置漂移，出个报告。

抬一层：**人做巡检会漏、会累、会因为「上次也是这样」而放过真问题**。原型 3 要证明的不是
「Agent 也能扫」，而是「把检查方法论固化下来之后，漏报/误报可以被量化、被回归、被改进」——
这跟原型 1 的「证据链 + 沙箱 + 闸门」、原型 2 的「成本账记未知而不记 0」是同一条价值观：
**宁可诚实标注不知道，也不编一个好看的结果。**

做完之后我希望面试官问「你怎么知道这个体检 Agent 没在瞎报」时，我能拿出一张
precision/recall 对照表，和一份公开的已知缺陷清单，而不是一句「我测过」。

## 三、方法与工具

### 数据契约（统一，检查器只认这个）

```python
Finding(
  id,            # 稳定去重键：checker + 目标 + 位置
  checker,       # 哪个检查器
  severity,      # P0 / P1 / P2
  category,      # credential / drift / exposure
  title,         # 一句话
  evidence,      # 可复核的原始事实（脱敏后），不写结论
  why,           # 为什么这个严重级别
  suggestion,    # 建议动作（脚本不做任何变更）
  meta,          # 机器可读附加字段
)
```

环境上下文 `Context` 是唯一输入。三个检查器都只从 Context 取数据、只读，
**任何检查器都不修改被检查对象**。这是硬约束，对应原型 1「agent proposes, human disposes」。

### 三个检查器（对齐骨架规划，但数据源换实）

| 检查器 | 数据源（真实可用） | 判什么 | 严重级规则 |
| --- | --- | --- | --- |
| `credscan` | 本地目录只读扫描 | 明文凭据入库 | 沿用 secret_scan：.env/prod 配置=P0，注释=P2，代码里带引号长字面量=P1 |
| `drift` | 160 Prometheus `/api/v1/targets`（只读 HTTP） | 抓取目标指向失联主机 / job 整体 down | 指向已失联 IP 的 target=P1；基线外新增=P2 |
| `exposure` | 从 targets 解析 instance 端口 + 基线白名单 | 端口暴露面与基线是否一致 | 基线外监听=P1；高危端口暴露=P0 |

### 严重级别（不许拍脑袋，写死规则）

- **P0**：明文凭据在配置文件/生产路径；或高危管理端口（如 2375/6379/9200）对外可达。
- **P1**：抓取目标指向已确认失联的主机；生产配置脱离基线；基线外新增的服务端口。
- **P2**：注释里的凭据残留；job 探测为 down 但主机本身可达（可能是采集侧问题，需人工判）。

### 外部验证（绝不让检查器自己评自己）

1. **黄金用例集**：手工造一个目录，已知「该报 N 条、不该报 M 条」，检查器必须对答案 100% 判对，
   否则先修检查器。这是元验证，对应 `verification/README.md` 里那条原则。
2. **160 真机对照**：跑一轮，人工逐条核对 32 个 target 的健康与指向，产出漏报/误报清单，不藏。
3. **噪声注入**：故意塞占位符、注释、压缩 JS，确认不误报。
4. **追问链**：报告出来后能就某条 P0 用自然语言问「怎么修」，走方舟 plan 真实 key；
   模型不可用时如实降级并标注，不假装成功。

## 四、野心目标 vs 普通版

| 维度 | 普通版 | 野心版（公开承诺，兑现不了就写进缺陷清单） |
| --- | --- | --- |
| 准确性 | 「能扫出问题」 | 黄金用例 100% 判对；160 真机漏报/误报逐条公开 |
| 可复跑 | 手动跑脚本 | 一条命令出 Markdown 报告 + JSONL 证据链，退出码即门禁 |
| 追问 | 无 | 自然语言追问走真模型，降级可观测 |
| 诚实度 | 报一堆告警 | 每条 finding 带「为什么会误报」的自评，未知就说未知 |

## 五、刻意不做（防范围扩大）

- 不做自动修复、不做写操作（连 touch 都不做）
- 不做 SSH 依赖（本机免密不通，采集全走只读 HTTP）
- 不做 Web UI（Markdown 报告 + JSONL 即可）
- 不接 GLM/DashScope（.env 里是占位符，实测 401，不编造渠道）
