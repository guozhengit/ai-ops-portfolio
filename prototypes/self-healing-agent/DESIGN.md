## 第一步 · 改写后的任务（高度：目标背后的目标）

**原任务（表层的写法）**：接 Prometheus 告警，Agent 自动诊断，输出修复建议。

**抬一层之后**：这不是「告警通知工具」，是**「让服务保持健康」**——再抬一层，是
**「建立一个可复用的『Agent 运维可靠性范式』」**：让每一个诊断结论都带完整证据链
（指标窗口 + 日志原文 + 时间线），让每一个修复建议都先在隔离环境里证明自己，
让每一个危险动作都过人工闸门。

**做完之后我希望发生的事**：
1. 面试官问「你们的 Agent 怎么保证不瞎说」时，我给的不是说辞，是可运行的范式
   ——诊断有证据、修复有沙箱回显、危险有闸门、质量有评测集
2. 这套范式能原样搬给原型 3 和未来任何 Agent 项目（体系 > 孤例）
3. 文章发出去后，评论区的问题是「怎么接入我的环境」，而不是「这也叫自愈？」

**适合抬层的判断**：这件事做完要面试讲、要写文章、要被别人复用——典型该抬层的任务。

## 第二步 · 方法与工具（深度：顶尖从业者会怎么做）

### 深度四问

1. **顶尖从业者会做哪些我没要求的事？**
   - 定义 SLO 并公开测量：定位准确率、误报率、MTTD（从告警到报告的分钟数）
   - 故障注入剧本化：每个场景有明确的注入命令、观察窗口、预期发现——可复现、可盲测
   - 事后复盘机制：Agent 漏报/误报的每个 case 都写进缺陷清单，而不是修完就忘

2. **从哪些最原始的材料入手？**
   - 真实 Prometheus 指标（160 主靶场），不是预录的数据快照
   - 真实容器日志（docker logs /loki 均可），允许带噪声、带无关报错
   - 真实告警时间线（Alertmanager webhook 原始 payload），不清洗

3. **用什么具体方法和工具？**
   - Agent 底座：agentscope-learning L20/L21 harness Team——按职能拆 member，
     每个 member 独立权限上下文（L21 已验证的安全链叠加）
   - 团队编排：triage（告警分诊）→ metrics-analyst（查指标，MCP 工具）→
     log-analyst（查日志，MCP 工具）→ remedy-planner（结构化方案：
     疑似原因/证据/建议动作/风险等级）→ sandbox-verifier（隔离容器试执行 + 回显）
   - 人工闸门：L9 HITL + L7 PermissionEngine——`agent proposes, human disposes`
   - 交付门禁：L22 的生产就绪 gate 思路搬进 verification/gates/

4. **除了你我，还有什么能证明结果是对的？**
   - 盲测：故障注入时**不告知**场景类型，看定位是否命中
   - 对照组：同一场景人工诊断记录 vs Agent 报告，逐项比对
   - 红队：喂假指标/噪声指标，验证不产生幻觉性结论（宁可说「证据不足」）
   - 评测集沉淀：5 场景剧本 + 评分脚本进 `verification/scenarios|scoring`，CI 可跑

### 故障场景（5 个，比原计划 3 个扩容——骨架省下的时间花在这里）

| # | 场景 | 注入方式 | 证据链要求 |
| --- | --- | --- | --- |
| 1 | 内存泄漏 | chaos-demo 服务随机 OOM | 内存曲线 + OOM 日志 + 重启时间线 |
| 2 | 慢 SQL | demo 服务内嵌慢查询开关 | 耗时指标 + 慢日志 + 连接占用 |
| 3 | 磁盘打满 | 日志膨胀脚本 | 磁盘用量曲线 + inode + 膨胀源定位 |
| 4 | 连接池打满 | 并发压测工具 | 池利用率 + 等待队列 + 线程栈 |
| 5 | Nacos 注册异常 | 停注册/心跳注入 | 注册表快照 + 心跳日志 + 流量影响 |

## 第三步 · 野心目标（抬一个量级，写下来就要兑现）

| 维度 | 普通版（够得着） | 野心版（公开承诺） |
| --- | --- | --- |
| 定位能力 | 3 场景定位 ≥2 | **5 场景盲测定位 ≥4，误报 0** |
| 响应速度 | 「能出报告」 | **MTTD ≤5 分钟**（人工基线 30 分钟，before/after 实测） |
| 安全性 | 「有审批闸门」 | **100% 建议动作沙箱先验证，0 次未审批生产动作**（有审计记录） |
| 可复用性 | 「一个 demo」 | **运维诊断评测集开源**（场景剧本+评分脚本+CI 门禁，属 verification/ 资产） |
| 传播 | 「写篇文章」 | **文章 1 篇 + 2 分钟演示视频**，至少 1 条外部真实互动 |

## 第四步 · 外部验证方式（绝不让 Agent 自己评判自己）

1. **盲测对照**：5 场景注入（类型对 Agent 保密），定位命中表 + 报告全文公开
2. **人机对照**：每场景留一份人工诊断记录（我自己先做），漏报/误报逐项列出，不藏
3. **红队噪声**：注入假指标、断网 MCP、半截日志三类干扰，期望行为 = 降级为
   「证据不足」而非编造结论；红队记录进 `verification/redteam/`
4. **CI 门禁**：评分脚本 + L22 gate 思路接入 CI，README 里的每个数字都能复现
5. **已知缺陷清单**：发布时公开当前未修复的缺陷，可信度 > 完美度

## 边界（刻意不做，防范围扩大）

- ❌ 自动执行生产修复（沙箱验证 + 人工审批就到头，自动执行进 roadmap）
- ❌ 多集群 / 多租户支持
- ❌ Web UI（报告输出为 Markdown + 截图，控制台可读即可）
- ❌ 通用告警平台（只接 Prometheus/Alertmanager 一条链路）
