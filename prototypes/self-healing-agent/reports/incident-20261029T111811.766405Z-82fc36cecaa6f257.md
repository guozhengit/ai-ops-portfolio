## 结论

告警**真实有效**：当前连接池占用确认为 `10/10`，与 ChaosPoolExhausted 触发条件一致。

从已采集到的靶场观测数据看，**直接触发因素是 `pool-exhaustion` 故障场景处于激活状态**；同一时刻 `slow-sql`、`nacos-flap`、`memory-leak`、`disk-full` 等其他故障场景均为 `0`，没有证据表明本次打满由慢 SQL、注册中心抖动、内存泄漏或磁盘满共同引发。

需要说明的是：当前环境可用数据面仅包含 `chaos_` 前缀指标，不提供应用日志、数据库日志或连接池内部明细接口。因此，可以确认“连接池被打满”和“pool-exhaustion 故障已激活”，但**无法仅凭现有数据进一步区分**连接被长期占用的具体业务机制：

1. 连接泄漏：连接借出后未正确归还；
2. 长事务 / 慢查询：连接被长时间持有；
3. 并发热点 / 流量突增：有限连接数被正常请求占满。

在没有 QPS 突增和慢 SQL 证据的情况下，证据更倾向于“连接被持续占用 / 未及时释放”类问题；但应用侧泄漏检测堆栈和事务日志是当前唯一缺失的定性证据。该缺口不影响 P1 告警成立和止血决策，根因修复阶段应优先补齐日志后再最终定性。

## 后续观察项

1. **连接池水位**：持续观察 `chaos_pool_in_use` 是否从 `10.0` 回落，并补充应用连接池 active / idle / pending / await 线程数。
2. **获取连接错误**：观察获取连接超时、等待时长、连接申请失败率是否在限流或关闭注入后下降。
3. **流量与 RT**：观察 QPS、接口 RT、慢调用比例，确认是否存在流量突增；若无流量突增而连接仍长时间占满，应优先排查泄漏或长事务。
4. **数据库侧指标**：观察数据库总连接数、活跃会话、平均事务时长、锁等待、慢查询数量，防止扩容后瓶颈转移至 DB。
5. **故障注入开关**：确认 `pool-exhaustion` 是否回到 `0.0`，并复核其他 chaos 场景是否仍全部为 `0.0`。
6. **日志补齐**：补充应用异常堆栈、连接泄漏检测日志、事务开始 / 提交 / 回滚日志、慢 SQL 日志，作为最终根因定性证据。
7. **参数与发布验证**：任何连接池参数、SQL、事务代码变更均应灰度发布，对比变更前后连接占用 P95 / P99、获取连接等待时间和错误率。
8. **应急防重试风暴**：限流和降级期间同步监控上游重试次数、请求积压和队列长度，避免恢复动作引发二次放大。
