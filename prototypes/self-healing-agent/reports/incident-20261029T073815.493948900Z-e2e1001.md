# ChaosMemoryLeak 诊断报告

- **告警**：ChaosMemoryLeak
- **fingerprint**：e2e1001
- **severity**：P1
- **现象**：内存泄漏，RSS 超 200MB，逼近容器限额

---

## 结论

**这是一次由混沌工程故障注入（memory-leak）引起的真实内存驻留事件，而非业务代码无界泄漏，但当前处于"注入已开启、从未关闭"的悬挂状态，且受害 Go 应用已不可抓取（疑似崩溃 / OOM / TargetDown），P1 成立。**

判定依据：

1. **根因明确为 memory-leak 故障注入**：权威的 `chaos_status` 显示 `active=["memory-leak"]`，其余所有场景（slow-sql / disk-full / pool-exhaustion / nacos-flap）均未激活（`disk_used_bytes=0`、`pool_in_use=0`、`nacos_registered=1` 正常），可排除慢 SQL、磁盘打满、连接池耗尽、Nacos 抖动。
2. **泄漏量与 RSS 完全相等，可解释全部 RSS 增长**：metrics 侧快照 `leak_bytes == rss_bytes = 62914560 (60MiB)`；logs 侧另一时点快照 `chaos_memory_rss_bytes == chaos_memory_leak_bytes ≈ 4.4040192e+08 (440.4MiB)`。两次数值差异来自观测时点 / 数据源不同（注入驻留块在持续累积），但共同点是 **RSS 增长 100% 由 leak_bytes 解释**。440.4MiB 已超过告警阈值 200MB。
3. **注入只开未关**：`chaos_fault_toggles_total{action="on",scene="memory-leak"}=1`，只有一次 `on`、没有 `off` 记录，说明故障未被回收，驻留块持续占用，这是 RSS 不断抬升、逼近限额的直接原因。
4. **受害应用已失联**：like-admin(192.168.1.159:8082)、like-front(:8084) `up=0`，TargetDown firing，应用自身 heap / GC / QPS 曲线缺失。因此**无法证明"业务侧无界单调增长"，也不能排除应用已 OOM / 崩溃**；但基础设施容器无一接近 OOM（最高 mysql 77.9%、grafana 77.3%），节点仅有 warning 级 ZktNodeMemoryHigh，说明压力集中在被注入的目标应用，而非整节点或中间件。

综合：**告警属实、根因为 memory-leak 混沌实验未关闭导致的一次性/累积性驻留块；首要处置是关闭/回收该故障注入并确认应用存活，而非先按业务代码泄漏排查。**

| 2 | **确认并恢复受害应用**：检查 like-admin / like-front 是否已 OOMKilled / 重启，必要时滚动重启 Pod，观察 `up` 恢复、RSS 是否回到正常水位 | 止血 | 中：重启造成短暂请求抖动 / 实例不可用，需确认实例数与流量承接 | **需要**：涉及业务实例重启，走变更审批并避开高峰 |

## 后续观察项

1. **注入关闭后 RSS 是否回落**：执行 off 后持续观察 `chaos_memory_leak_bytes`、`chaos_memory_rss_bytes` 与容器 `container_memory_usage_bytes`，确认驻留块被释放、RSS 回落到基线；若不回落，需排查是否演变为真实泄漏或需重启释放。
2. **应用存活与 TargetDown**：确认 like-admin(:8082)、like-front(:8084) `up=1`，TargetDown 清除，QPS / GC / heap 曲线恢复可抓取。
3. **是否发生过 OOMKilled / 重启**：在容器状态 / Events 中确认重启次数与 lastState=OOMKilled，评估是否触及限额导致被杀。
4. **节点内存压力**：ZktNodeMemoryHigh(warning) 目前仍 firing，观察动作 1/2 后节点内存是否缓解，避免恢复后再次逼近节点限额。
5. **ChaosMemoryLeak 告警规则本身**：当前 Prometheus ALERTS 中查不到该告警、也无 chaos_ 前缀指标（metrics 侧 group by __name__ 为空），但 logs 侧可查到 chaos_* 原文——存在指标注册 / 数据源不一致，需核实告警评估所用数据源，避免"告警在响、面板查无此指标"导致后续无法回溯。
6. **演练收尾审计**：核对 `chaos_fault_toggles_total` 中 on/off 是否成对，排查是否还有其它场景的悬挂注入。
