# 诊断报告：ChaosMemoryLeak（fingerprint=d12s1，severity=P1）

## 结论

**告警属实，确诊为内存泄漏，且泄漏当前仍在持续。**

- 故障根源是演练场景 **`memory-leak` 故障开关处于 active 状态**（`chaos_fault_active{scene="memory-leak"}=1.0`），且该开关历史上 **on 2 次 / off 1 次**——曾被关闭后又被重新打开，因此故障复发并持续。
- 当前进程 RSS = 泄漏持有内存 = **723,517,440 B ≈ 690 MiB**，为 200MB 告警阈值的 **3.45 倍**。
- `chaos_memory_rss_bytes` 与 `chaos_memory_leak_bytes` **完全等量**，说明 RSS 增量 100% 来自被持续持有、**GC 不可回收**的对象（强引用 / 集合只增不减型），可排除缓存抖动、临时对象堆积等自愈性原因。
- 目前**尚未触发 OOMKill、也无进程重启**，但 RSS 持续逼近内存上限，若不干预将最终 OOM。
- 已排除其他并存故障：slow-sql / nacos-flap / disk-full / pool-exhaustion 活动位均为 0。

> 证据局限：metrics 独立趋势分析任务（task-2）异常结束、未提交有效结果，因此「线性/阶梯」增长形态与 GC 次数/耗时未获独立趋势复核；但 logs（task-3）已直接从指标端点取得逐字原文，remedy（task-1）也据此交叉确认，结论本身证据充分，仅增长曲线细粒度形态留作后续观察项。

## 后续观察项

1. **RSS 是否在 off 后回落**：连续观察 `chaos_memory_rss_bytes` 与 `chaos_memory_leak_bytes` 是否同步下降；若开关 off 但 RSS 不回落，说明已注入对象未释放，必须重启并据 dump 修复演练/业务代码。
2. **故障开关最终态**：确认 `chaos_fault_toggles_total` on/off 计数平衡且 `chaos_fault_active{scene="memory-leak"}=0`，防止再次被自动/误操作置 on。
3. **补齐独立指标趋势（弥补 task-2 缺口）**：拉取 RSS/heap 的时间序列，确认增长形态（线性=持续按速率分配；阶梯=周期性批次泄漏），并复核 GC 次数与耗时、GC 后堆占用是否不回收。
4. **OOM/重启事件监控**：盯 OOMKill、容器 restart 计数与内存 limit 余量，RSS 已达阈值 3.45 倍、逼近上限，属 P1 高风险，处置不应拖延。
5. **heap dump 分析结论闭环**：明确泄漏对象类型与持有链，回归后在预发重新演练验证「注入→关闭→内存可回收」。
6. **防复发**：为该演练/相关长生命周期集合加入内存增长告警阈值分级、缓存上限/TTL 与自动化开关回收校验。
