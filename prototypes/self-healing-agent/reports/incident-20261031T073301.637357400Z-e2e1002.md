## 结论

1. **根因（高置信）**：这是一次**注入型的连接池耗尽（pool-exhaustion）故障**，连接被一次性占满并**持续持有不归还**，而非流量增长、慢查询/长事务或代码级连接泄漏的自然演化。
   - `chaos_fault_active{scene="pool-exhaustion"} 1.0`，其余 4 个 chaos 场景（slow-sql / memory-leak / disk-full / nacos-flap）全为 `0.0`；
   - `chaos_fault_toggles_total{action="on",scene="pool-exhaustion"} 1.0`，注入开关创建于 **2026-10-31T07:28:09Z**；
   - `chaos_pool_in_use` 在 **07:28:57Z(0) → 07:29:17Z(10)** 之间 **20s 内阶跃至 10**，此后恒定不回落（`changes(...[10m]) = 1`）。
2. **打满起始时间**：约 **2026-10-31T07:29:0xZ**（采集时刻 07:31:27Z 前 130–150s），滞后注入开关约 50–70s。
3. **饱和程度**：池占用 **10**，持续满占用。**注意**：Prometheus 未暴露池上限指标（无 `chaos_pool_max`），"100% 饱和" 属靶场语义推断（若 maxPoolSize=10 则 ≈100%），**不是直读值**。
4. **是否仍在恶化**：**否，但未解除**。阶跃后恒为 10、零抖动，属**持续饱和（sustained saturation）**而非持续恶化；只要连接不释放，新请求获取连接超时的条件持续存在。
5. **排除性结论**：QPS 平稳（1m=31.98、5m=31.98、1h≈32.2 /s）→ 非流量型；DB 查询 P50=25.6ms / P95=48.7ms / P99=79.1ms、>100ms 仅 0.0115%、>1s 为 0、`slow-sql=0` → 非慢查询/长事务型；`leak_bytes=0`、RSS 10min Δ=0 → 非内存侧诱因。
6. **分歧裁定（metrics vs logs）**：metrics 判定为"注入型 held-connections"，logs 表述为"连接泄漏 / 长期占用未归还型"。二者**证据完全一致**（同一批 `chaos_*` 原始行），差异仅在标签：logs 的"泄漏型"应理解为**连接被长期持有不归还**这一现象，而**不是代码缺陷导致的渐进式泄漏**——metrics 的 `changes=1` 单次阶跃、20s 完成、无爬升斜率，正是排除"代码泄漏"判据的依据。**最终裁定：根因 = chaos 注入的 pool-exhaustion（连接持有不释放）；代码级泄漏仅为"若注入器模拟泄漏行为则需同步加固"的次要方向。**因此 remedy 方案中的**分支 C 主线降级为加固项**，方案主线应改为"确认/关闭注入窗口 + 连接归还与超时加固"。
7. **证据限制（必须声明）**：
   - 指标侧缺 **idle / pending 等待队列 / 获取连接 P50-P99 / 获取超时计数 / 池上限 / DB max_connections 占用**（`chaos_*` 全集仅 10 个指标名，已全量枚举验证）→ "获取连接超时"**无法从指标直接计数验证**，仅由池饱和 + 告警语义佐证；
   - logs worker 实际**无日志检索能力**，未取得应用 HikariPool 异常栈、DB `too many connections`、网关 5xx 原文（其诚实声明未编造证据）→ **影响面（哪些接口/租户）与泄漏代码路径仍待补采**；
   - 指标为**单点快照**，无法给出告警前 1 小时的完整池使用率曲线。
