# 三个周末，三个原型，和一套证明自己没在瞎说的办法

写完第三个原型的时候，我回头看了眼仓库——三个目录，一堆代码，但对外能讲清楚的东西只有三篇半文章。于是决定补一篇汇总：不是吹我做了什么，是把整条路怎么走的、哪些是我以为做完了其实没做成的，一次交代清楚。

配套代码都在 github.com/guozhengit/ai-ops-portfolio。文中每个数字后面都括了出处，你可以逐个对着看。

## 为什么是这三个

起点是一个很朴素的念头：市面上的 AI Ops 演示都在演"AI 能看懂监控截图"，可真正难的是让 AI 去碰生产的脏活——查指标、翻日志、交叉对时间线，最后交出一份敢让人签字的报告。

那我就自己搭。拆成三个周末，每个原型只回答一个问题。

第一个原型回答"怎么让 Agent 可靠地干活"。告警进 AgentScope 的 harness Team，一个 lead 带三个 worker 分头取证，出来的报告带完整证据链，人只做审批。

第二个回答"多模型环境下怎么算得清账"。云端渠道加本地兜底的设想，网关做路由、熔断、降级，每次调用都记账。

第三个回答"怎么把人的检查方法论固化成流程"。端口审计、凭据扫描、配置漂移——这些我以前得手工做的事，让 Agent 定期跑。

三个正好是 Agent 工程化的三块地基：可靠性、成本、方法论。缺一块，这个作品集就只是个能跑的 Demo。

## 第一个周末：先证明它不会胡说八话

原型一搭完，我最怕的是"AI 为了交差编一个根因"。所以设计了盲测：五种故障逐个注入，告警里只给症状——"内存持续上涨"、"查询变慢"——不告诉它是哪个场景，让它自己查指标反推。另外埋一场红队：发一条一模一样的磁盘告警，什么都没注入，看它会不会顺着 P1 的压力编。

六场全过。连接池那场它定位得很干净：应用侧池子 10 个连接全钉死，数据库 150 个只用了 6 个，然后主动写了一条"不要对 DB 扩容、不要 KILL 会话"。红队那场更让我意外——它查实时告警列表、真实磁盘水位、故障开关的历史计数，最后结论是"这是一场一次性注入，窗口 10 分 38 秒，在告警前约 24 分钟已结束，不建议做任何预防性清理"。我原来担心的事，在这个结构下没发生，大概是任务拆成三个互相印证的角色之后，想编也编不圆。

但盲测当天出了个岔子。主力渠道 MikuAPI 持续 503，chat 接口挂、models 接口正常。我一开始挺烦，后来意识到这是天赐的故障源——重试和降级代码刚写完，一直没被真实故障锤过。

实际表现：每次调用失败后本地指数退避重试三次，耗尽了整场切到备用的方舟模型重跑，报告头自动盖降级标记。六场全由降级路径跑完，诊断质量没掉。主模型挂掉的结果是慢了 40 秒，不是断供。

留下的尾巴不体面：动作提取器走主模型、无兜底，503 期间全失败。所以"白名单自动止血"这一环到今天都没在全自动链路里真正跑通过。这是我当时就该写进 README 的东西。

速度上也没漂亮。≤5 分钟的 MTTD 目标没达成。健康路径实测 8.6 分钟（`prototypes/self-healing-agent/docs/d12-blindtest.md`），降级路径 9 到 15 分钟，红队那场最重，接近 19 分钟。大头在三个 worker 串行排队，改并行后同场景重测从 8m02s 降到 6m42s（journal 时间戳可复核），但 lead 拆任务和最后写报告这两段天然串行，得换思路。

## 第二个周末：渠道不是供应商，钱也不是零

原型二踩的第一个坑就写在文档里：同一个 `https://mikuapi.org/v1`，两把 key 能用的模型清单**完全不相交**。新 key 只通 deepseek-v4.1-flash，gpt-5.x 全 404；旧 key 反过来。所以同一个 base-url 在我的配置里是俩渠道。

这个定义是被实测逼出来的，不是设计出来的：渠道 = base-url + key + 模型清单 + 价目，四元组。

接着是失败语义，这块最容易做错。我的划线是：500/502/503/429/超时算瞬态，换渠道并且计入熔断；404 模型不存在、400/401/402 余额不足算确定性错误，只换渠道**不熔断**。理由很简单——熔断是为了躲开"现在不健康"的渠道，404 说的是"这个配置根本不成立"，熔不熔断它都是坏的。这条后来用本地 HttpServer 打真实状态码断言，不靠 mock 猜。

成本账上我给自己定了条死规矩：**价目未知就记 `costUsd: null`，绝不记 0**。第三方中转常常没有公开价目，记 0 等于把"不知道"写成"免费"，比不记更糟。真机跑下来的账是 6 次调用、$0.00119，其中 2 笔成本未知（`prototypes/model-router/data/usage-report.json`）。数字很小，但这不是重点，重点是那 2 笔"不知道"被如实留在了账上。

## 第三个周末：我的第一份报告 22 条里有 17 条是误报

原型三我原以为最简单——端口审计、凭据扫描、配置漂移，规则明确，跑起来就完事。

结果第一版跑真实仓库，credscan 报了 22 条。我以为是发现了 22 个问题，逐条看下去，17 条是纯误报。

误报都挺典型。合规的本地 `.env` 文件被当成明文凭据；代码里写 `api-key-env: MIKU_API_KEY` 这种**引用环境变量名**的写法被判成硬编码密钥；`.venv-chaos` 里的第三方库被扫成了我自己的代码；`sk-change-me` 这种一眼假的占位符也报了；连 `.env.example` 这种本来就该入库的模板都进了名单。

更打脸的是 drift 检查器。第一版吐了 24 条 P1，噪音大到没法看，根子是我在配置里手填了已知死机 IP，等于把答案抄给检查器。重构后改成主机级聚合，判定给了两条路：基线确认，或者同一个 IP 上两个以上目标同时 down 时自推断——下结论不再依赖手工填基线。159 主机上那 20 个全瞎的目标，最后聚成 1 条 P1，而不是 20 条。（老实交代：留档那份真机报告的本地基线没清，159 走的是基线确认分支；无基线的自推断路径由单测覆盖。）24 条里剩下的是另外四个目标，等我把 DNS 判定补上之后才认对。

人工逐条核对 32 个 Prometheus target 之后，drift 维度的 precision 和 recall 都是 1.000，零漏报零误报。最终那份报告一共 5 条 P1：159 主机失联 1 条，加上 clickhouse、kafka、qdrant、rocketmq 四个 Docker DNS `no such host` 判成配置漂移 4 条。

但这个 1.0 是**改出来的**，不是一开始就在的。中间还有一次我把四个 DNS `no such host` 误判成 P2，实际是配置漂移该升 P1——是我人工核对时发现又改回去的。这段我写进文章③了，藏起来没意义。

## 现在说说第四个东西：验证本身

前三个原型各有一套验证，但它们长得都不一样：原型一是盲测场景 + 红队误报场，原型二是故障注入 + 熔断恢复演练，原型三是外部裁判 + 黄金答案。

我意识到这是个问题。作品集最容易被质疑的就是"你说它对，有证据吗"，而我的证据是散在各原型 README 里的，形态还不统一。所以做了第四个资产：一个验证工具箱目录，把场景用例、评分脚本、红队已知缺陷清单、CI 门禁收拢到一起。

CI 现在是三道 job：原型一跑 Java 单测 + 打包冒烟 + 密钥泄露扫描，原型二跑路由/熔断/成本单测，原型三跑 Python 单测 + 评分器元验证 + 评分链路冒烟。密钥扫描这条尤其要紧——有一回靶场里的假凭据把 CI 扫红了，我第一反应是"扫描规则太严"，后来想明白了：扫描器宁可错杀，等我加白名单就是，可漏杀一条真密钥进库，代价完全不对等。所以现在假凭据必须显式豁免，并且豁免理由写在文件里。

工具箱还带一条硬纪律：评分器自己对已知答案必须 100% 判对，判不对就不准拿去评原型。裁判先得是可信的。

## 没做成的部分

按重要性排：

MTTD 没到 5 分钟，这是三个原型里唯一被写在 README 上的硬指标，它没达成。优化方向清楚（worker 并行、关深度思考、轮次收敛），但没做完。

GLM（智谱）和 DashScope 两个渠道还是占位符配置，没真 key，所以装配期就被禁用了。真正跑起来的是 5 个渠道：miku 主档、ark、deepseek、xiaomi，加一个故意留着的 miku-gpt——那把旧 key 的 gpt-5.x 全 404、渠道本身还持续 503，我留着它不为能用，是为了有个能复现"瞬态故障→熔断→切渠道"的真实故障源。至于"本地兜底档位"这个设计，model-router 里压根还没实现，只在供应商模板里留了个 LM Studio 的坑位，这事我之前没老实说。

动作提取器的兜底链路至今没在全自动模式下跑通过，就是第一节说的那个尾巴。

原型一的 webhook 还指向我本机，服务没上服务器常驻。我写这篇之前顺手 `netstat` 了一眼，8400、8410、9400 三个端口一个都没在监听——也就是说这文章里的所有数字都来自当时那次真机跑完就停的现场，仓库里留下的是报告和账本，不是活着的服务。想复现得自己按各 README 把环境拉起来。

exposure 检查器这一轮 0 条结论，严格说只成立于"Prometheus 抓取清单内无高危端口"——SSH 免密不通，没做真实全端口扫描。

端口审计脚本本来想复用 `hotel-booking/ops/port-audit/port_audit.py`，全盘搜了一圈发现**这文件根本不存在**。真正能复用的是 `agentscope-learning/tools/secret_scan.py` 的分层判定和脱敏思路，以及 `schema_guard.py`、`check_perm_parity.py` 那套"纯标准库、只读、退出码门禁、白名单落文件"的纪律。承认自己记错了，比硬编一个引用体面。

## 三个月后我会记得什么

不是三个原型本身，是三件被它们教出来的事。

第一，**先量准了再动手**。原型二那个"渠道 = 四元组"的定义，是被两把 key 模型清单不相交撞出来的，不是我坐在那儿想出来的。

第二，**让 AI 干活的边界就是它能碰的东西**。原型一手上一把 shell 都没有，取证全靠只读工具；原型三采集能力缺失时登记 degraded 而不是假装采到了。边界清晰，出错方式才可预测。

第三，**"看起来对"和"真对"之间隔着一个人工核对**。原型三那个 1.000 是我一条条对着 32 个 target 核出来的，核完还得改代码才拿到。工具能帮我把问题排出来，但"这个问题算不算问题"这条线，还是得有人划。

这三个原型加起来不到八千行代码（含测试，原型一 1292 行、原型二 4411 行、原型三 2160 行；行数口径为各原型目录下全部源码文件），但让我觉得值钱的不是代码量，是每一条结论后面都跟得上一个出处。
