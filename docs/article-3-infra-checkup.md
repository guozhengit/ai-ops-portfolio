# 我让 AI 给运维做体检，第一份报告 22 条里有 17 条是误报

原型 3 做完了。这篇不写它多能干，写它第一版有多不靠谱，以及那些不靠谱是怎么被一条条揪出来的。

配套代码：github.com/guozhengit/ai-ops-portfolio 里的 `prototypes/infra-checkup`，报告原件、黄金用例、人工核对记录都在仓库里，欢迎对着看。

## 起因，和两个一开始就错了的假设

做原型 1、2 的时候我一直在想一件事：AI 干的活怎么才算靠谱。原型 1 用证据链和人工闸门回答，原型 2 用成本账和「价目未知就记未知而不记 0」回答。到原型 3，我想把这个问题再往前推一步——**漏报和误报能不能被量化、被回归、被改进**，而不是我嘴上说一句「我测过」。

体检这个活适合拿来验证。端口审计、扫明文凭据、查配置漂移，人做起来是重复劳动，但判断标准全在老运维脑子里：什么算严重、看到之后先查什么。我想把这套东西固化成代码。

结果刚动手就发现规划阶段的两个假设是错的。骨架 README 里写「复用 hotel-booking 的 port-audit.py」，我把整个 D 盘搜了一遍，这文件根本不存在，那句话是张空头支票。真正能继承的是另外三份脚本：一份凭据扫描器（分层判定、脱敏、占位符不算违规），两份一致性守卫共有的纪律——纯标准库、离线只读、退出码即门禁、白名单豁免必须落文件并注明归属、代码里绝不写死仓库外的绝对路径。这套方法论比一个不存在的脚本值钱多了。

第二个错是靶场。骨架写「159/160 真实环境」，实测 159 已经彻底不通，ping、22、9091 全断，本机 DHCP 之后也从 .159 变成了 .16。真正活着的是 160，但它 SSH 免密用三把私钥全被拒，只有 Prometheus 的 9091 只读 HTTP 开着。所以采集层我干脆只走只读 HTTP，不赌 SSH。

## 怎么搭的

一条命令跑完，出一份只读报告。Python 3.13 纯标准库，没装任何第三方依赖，CI 里也能跑。检查器只认一个 `Context` 进、`Finding` 出，谁都不许改被检查的对象——跟原型 1 那句「agent proposes, human disposes」是同一条边界。

三个可插拔检查器：`credscan` 扫明文凭据（命中只报键名加长度，绝不打印原文，否则自查报告自己就成了新的泄密源）、`drift` 看配置漂移和抓取健康、`exposure` 看端口暴露面。注册表是显式的，少注册一个会直接报错，不会静默少跑一项。报告按 P0/P1/P2 分级，JSONL 证据链只追加，有 P0 或 P1 就退出码 1，能直接当 CI 和 cron 的门禁。报告发出后还能就某一条用自然语言追问「具体怎么排查」，接的是真模型。

采集能力缺什么就在报告顶部写什么，绝不静默跳过假装查过了。这条我盯得最紧——体检工具最怕的就是「没查」和「查了没问题」长得一模一样。

## 第一次扫自己的仓库：22 条，17 条是误报

工具写完，我没拿玩具数据糊弄，直接扫整个作品集仓库。第一版报了 22 条，看得我脸有点热。

逐条翻下来，17 条是彻底的误报，得删；另 5 条是误分级，得重新定性。`.env` 里的 ARK、MIKU 这些真实渠道 key 被当成「明文入库泄露」——可那文件本来就被 `.gitignore` 盖着，在里面放真 key 正是设计意图，我等于把合规做法当成了事故，这 5 条属于后者。`application.yml` 里的 `api-key-env: MIKU_API_KEY` 被报成明文，可那个值是个环境变量**名**，是告诉程序去哪儿取 key，不是 key 本身。`.venv-chaos` 里 jinja2 的一堆 `TOKEN_BLOCK_BEGIN` 常量被扫了出来，第三方库的源码压根不该进扫描范围。`sk-change-me` 因为前面带了个 `sk-` 前缀，躲过了我那条以 change 开头的占位符正则。还有 `.env.example`，它被 `!.env.example` 特意放行、本来就该入库，却被报成「未忽略，有泄露风险」。

这几类我一类一类改：用 `git check-ignore` 精确判定被忽略的 `.env`，降级成提示并改掉措辞；认出纯大写下划线标识符是变量名引用；把 `site-packages` 这类第三方目录加进跳过名单；占位符改成片段匹配而不是锚定开头；入库模板加白名单。改完再扫，22 条告警里 17 条纯误报被删干净，剩下 5 条从 P0 降成 P2，措辞也改成「这文件已被 gitignore 覆盖，放着没事，确认别误提交就行」。纯误报清零。

有个细节我挺在意：一开始为了让靶场的假 `.env.prod` 能进 CI，我在根 `.gitignore` 里给它开了 `!` 例外，结果它反而从「被忽略」变成了「未忽略」，分级跟着变了。我最后把靶场的分级逻辑固定成「强制按未受保护处理」，不依赖那个环境里 git 命令在不在，否则本地绿、CI 红的老毛病又要犯。模拟 git 完全不可用的情况跑了一遍，45 个测试照样全绿。

## drift 那边也没好到哪去

扫仓库这边修完，监控那边第一版更离谱：160 的 32 个抓取目标，它报了 24 条 P1。

问题出在我把 192.168.1.159 上那 20 个全 down 的目标**逐条**报了出来，还依赖我手工填进基线的「已知失联主机」来判定。说白了，它只是把我早知道的那个死 IP 复述了一遍，这不叫固化方法论，这叫抄答案。

我重写成主机级聚合，判定给了两条路：同一个 IP 上多个目标同时 down 就自己推断主机级故障（自推断优先），基线只做确认增强——人不再需要提前告诉它哪台死了。改完 24 条收敛成 1 条。自推断这条路有单测背书：把基线清空，159 照样被认出来。不过有一句得老实说：10 月 30 号那份留档真机报告里，我本地基线没清，159 走的是基线确认分支——JSONL 的 meta 里 `self_inferred: false` 记得清清楚楚，两条路哪条开的火，看 meta 就知道。

还有个更隐蔽的误分级。clickhouse、kafka、qdrant、rocketmq 四个目标 down，我第一版降成 P2「可能是采集侧问题，需人工确认」。后来盯着 `lastError` 原文看了半天才发现，四条全是 Docker 内嵌 DNS 的 `no such host`——这根本不是「服务可能临时挂了」，是服务发现里写了一个压根不存在的容器名，确定性的配置错误。补上 DNS 判定才升成 P1。工具把确定的事说成不确定，也是一种不诚实。

## 追问链卡在代理上

诊断报告出来后能追问「这条怎么修」，这部分接的是方舟真模型，中间踩了个方向完全拧着的坑。

内网 160 采集必须**绕开**环境代理，否则拿到的是代理劫持的假响应；外网方舟调用恰恰**要走**代理，而 Python 的 urllib 在这个环境走代理会一路卡到超时，curl 走同一个代理 1.8 秒就 200。同一个 opener 不能内外网通吃，这两处必须是反的。最后追问链主通道改成 curl 子进程，key 通过临时配置文件传、绝不进 argv(进程列表看得见)。豆包 seed 是推理模型，不关深度思考会先耗十几秒到几分钟想，`max_tokens` 给小了正文直接被思考吃光——原型 2 就踩过 64 被截断。加上 `thinking: disabled` 之后，十几秒出一份按执行顺序的排查步骤。

三条路径我都实测过：真 key 成功(14.8 秒)、没 key 或超时如实降级不编答案、被扫描环境里混进「忽略以上指令」时反注入自检直接拦下。模型给的东西一律标注「未经外部验证」，不跟确定性检查器的结果混为一谈。

## 那个 1.0 是改出来的

人工逐条核对完 32 个目标，drift 维度的 precision 和 recall 都是 1.000，漏报 0、误报 0。最终真机报告：P0 零条、P1 五条(159 主机失联加四个 DNS 配置漂移)、P2 五条(合规的本地密钥文件)。

但我得把话说清楚：这个 1.0 不是第一版跑出来的，是被上面那两轮打脸改出来的。要是我只贴最终这张漂亮的表，这文章就白写了。评分器自己也过了元验证——对已知答案的用例必须 100% 判对，否则先修评分器再评原型，不然就是让工具自己给自己打分。

数据都能自己复核。人工核对记录、黄金答案、评分脚本都在 `scoring/` 里，`python scoring/run_score.py` 连 160 重跑一遍就能对。45 个单测、`-W error::ResourceWarning` 下没有未关闭的文件句柄，真机报告留档在 `reports/`。

## 还没做完的

有几件事我特意没做，也不打算藏。exposure 只依据 Prometheus 的抓取清单判定，SSH 免密不通，没做真实全端口扫描，所以「零条高危端口」只说明抓取清单里没有，不等于 160 上没暴露，每条这类发现都标了「未验证暴露」。基线里的目标清单是空的，本轮不做「该监控却没配」的增删比对，报告顶部有降级提示。主机级自推断要求同 IP 且至少两个目标同时 down，单目标的主机失联会漏成 P2。评分口径只覆盖 drift 维度，凭据扫描靠 45 个黄金用例保证——真仓库那几条 P2 是提示性发现，没有独立的二值真值，不该硬塞进 precision/recall。完整的坑挂在 `verification/redteam/known-defects.md`。
