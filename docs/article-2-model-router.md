# 我给自己搭了个模型总闸，第一课是渠道不等于供应商

原型 2 做完了，这篇记录它从哪来、被什么逼出了哪些设计、以及为什么账本上留着两个「不知道」。

配套代码：github.com/guozhengit/ai-ops-portfolio 里的 `prototypes/model-router`，渠道验证记录、账本原件、演练数据都在仓库里，欢迎对着看。

## 起因：被 503 摁着头做的决定

上一个周末给原型 1 做盲测，正赶上主力渠道 MikuAPI 持续 503：六场盲测全被赶到备用的方舟模型上，动作提取器走主模型、没兜底，全灭。当时我是靠「.env 里换一行注释」这种手工操作在几个供应商之间搬流量的——搬一次重启一次，搬到第三次我就知道这事不能这么干了：模型渠道需要一根总水管，而不是四根随时断水的细管子。

【口述待补：决定动手那天更具体的场景——当时手头正被什么卡着、为什么选了改造而不是重写】

底子是现成的。之前写过一个 tts-router：语音合成的多引擎路由，已经把「多渠道网关」最难的部分写完并且被真实使用锤过——优先级选路、熔断加冷却、计量账本、网关鉴权、控制台，全套都有。所以这次不是从零写，是把「引擎」这个抽象从音频合成泛化成一切 OpenAI 兼容调用：`SpeechCommand` 换成 `ChatRequest`，`/v1/audio/speech` 旁边长出 `/v1/chat/completions`，JDK 从 21 拉到 25，端口 8410。语音那套（ffmpeg 转码、WAV 拼接）冻结不删，控制台里留一个「语音合成 · 冻结」的 Tab 给它。

## 第一课：渠道不是供应商

改造完第一个真机验证就翻车了。同一个 `https://mikuapi.org/v1`，新旧两把 key，我以为是同一个渠道的两把备用钥匙。实测结果：

| 模型 | 旧 key | 新 key |
| --- | --- | --- |
| `gpt-5.4-mini` | 503（认这个模型，上游挂了） | 404（这个组根本不认） |
| `deepseek-v4.1-flash` | 404（不认） | 200（正常） |

错误信息里那句 "not supported by any configured account **in this group**" 就是答案：同一个平台底下，不同 key 分属不同 group，group 决定你能用什么。两把 key 的权益**完全不相交**——同一个 baseUrl 配两把 key，就是两个渠道，不是两个备份。

所以「渠道」在我的路由器里最终长成了四元组：**base-url + key + 模型清单 + 价目**，缺一个都不成立。这个定义不是设计出来的，是被实测摁着改出来的。

顺带留了个故意的脏东西：旧 key 挂成独立渠道 `miku-gpt`（priority 9），它的 gpt-5.x 全 404、渠道本身还持续 503——留着不为能用，为的是手里有一个能复现「瞬态故障→熔断→切渠道」的真实故障源。新 key 那边则贡献了另一种病：15 次采样里 1 次 502，加上那串 404。两条失败路径各有一个真实样本，演练才完整。

## 第二课：404 和 503 是两种病

失败语义是最容易做错的地方。我的划线：

- **瞬态**——500/502/503/429/408/超时：渠道「现在不健康」，换渠道，并且计入熔断计数；
- **确定性**——404 模型不存在、400/401/402 参数和余额问题：渠道「配置根本不成立」，只换渠道，**不熔断**。

理由很朴素：熔断是为了躲开「现在病了」的渠道，一个 404 的渠道你怎么熔它都是坏的，熔断它只会白白把恢复流程跑一遍。

这条线划完就固化成测试：`HttpChannelStatusTest` 在本地起一个真 HTTP 服务，把当时 MikuAPI 返回的错误原文原样重放，404/400/401/402 断言确定性、500/502/503/429/408 断言瞬态——不靠 mock 猜语义。恢复那边有 `ChannelRecoveryTest`，用本地 HttpServer 造一个「先坏后好」的渠道，验证开闸→冷却→半开→回主档整条链真实走得通。

再往前走一步：404 根本不该等到请求期才发现。所以加了启动期能力探测——拿 `GET /v1/models` 把每个渠道声明的模型清单校准一遍，没权益的模型直接摘掉，省掉一次注定失败的跨渠道跳转。但探测本身也可能失败（方舟的 plan 专用端点就没法探测），规则是探测不出结论就**保守保留**声明，宁可留一个可能 404 的条目，不误杀一个真渠道。

## 第三课：未知不等于免费

先看一笔小账。非流式返回的 usage：

```json
{"prompt_tokens":37,"completion_tokens":22,
 "completion_tokens_details":{"reasoning_tokens":19}}
```

22 个输出 token 里 19 个是推理 token。这是推理模型，输出侧单价乘的是含推理的总量，比普通 chat 模型贵一截——只看单价表算成本，账一定是错的。

然后是更根本的问题：价目从哪来。MikuAPI 是第三方中转，没有公开价目。配置里最初写死的 `0.30 / 1.20` 是我拍的，不是查到的。按「成本数字必须有出处」的规矩，这种数字不能要。所以最后定死一条纪律：**价目未知就记 `costUsd: null` 加 `costKnown: false`，绝不记 0**——记 0 等于把「不知道」写成「免费」，比不记更糟。

流式那边还有个纯工程问题：SSE 一路透传给客户端，token 数在哪？答案是 usage 出现在带 `finish_reason: stop` 的那一帧里。我在旁边接了个抄表的（`SseUsageStream`），字节原样透传一字节不少，顺手把最后一帧的 usage 抄进账本。真流量实证：263 帧、74KB 的流式响应，账本里 promptTokens 35、completionTokens 262——token 精确了，成本**依然**是 null。价目未知这件事，不会因为 token 数知道了就变得已知。

跑下来的真实账本（`prototypes/model-router/data/usage-report.json`）：6 次调用、合计 $0.00119，其中 2 笔成本未知；方舟 3 次平均 20.9 秒、最慢一次 55.4 秒，MiMo 835 毫秒 $0.000005。数字小到可笑，但这不是重点——重点是那 2 笔「不知道」被如实留在了账上，聚合脚本里它们单独计数，不混进总额。

## 面板是给重启时刻的自己用的

控制台做了双 Tab：「对话路由 LLM」是主轴，渠道健康表带今日调用和成本，统一模型清单和 `/v1/models` 同源，下面一个真发请求的试调面板，显示走了哪个渠道、耗时多少、token 和成本几何。中间被真实浏览器截图打过一次脸——自己看着没问题，截图里白屏，才修掉一批只在真实环境现形的 bug。流式回复改成增量渲染，不再等完整 body 攒齐才上屏；静态资源加了 no-cache，省得改了代码浏览器还端着旧的 app.js。

## 两个工程上的坑

一个是 H2 文件锁。Windows 下 Bash 后台任务停止只杀外壳，Java 子进程继续活着占端口、锁着 H2 数据库文件，新起的实例「秒启动」其实是老实例在应答——识别信号是「启动太快」和「渠道凭空消失」。现在换实例前先查端口占用，成了肌肉记忆。

另一个是 `.gitignore`。根上有一条 `**/apiKey*`，Windows 文件系统大小写不敏感，它把网关鉴权过滤器 `ApiKeyAuthFilter.java` 静默吞了——本地一路绿，CI 编译红。排查清楚后加了 `!prototypes/model-router/src/**` 例外。教训是：`.gitignore` 的规则会跨层级生效，交付前必须复查暂存区里实际有什么文件，不能信「我写过的规则」。
